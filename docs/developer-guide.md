# Developer guide

This guide describes the repository architecture, the engine bridge protocol,
how to run the tests and how to integrate a further DESERT module. The public
Python API is documented in [api.md](api.md); configuration in
[stack-configuration.md](stack-configuration.md).

## Design rules

- HoloOcean 2.3 executes physics, sensors, collisions and the vehicles' PD
  control. DESERT 4.0 / NS-MIRACLE executes the complete network stack. Python
  never computes deliveries, losses, interference, propagation delays or
  routes, and there is no Python fallback network.
- Configuration enters the engine only as whitelisted values: classes,
  libraries and numeric Tcl constants generated by the stack builder. The client
  can never send arbitrary Tcl.
- Applications see only their own pose and their own communication handle;
  the fleet ground truth stays in the orchestrator.
- Unobservable counters are `null`, not zero; no cause is invented for a loss.
- The upstream DESERT sources and libraries are not modified. Project classes
  are subclasses or separately named copies compiled into `libholobridge.so`.

## Data path and synchronisation

```text
HoloOcean (host) <-> HoloOceanAdapter
                        |
               SimulationOrchestrator <-> CommunicationManager <-> applications
                        |
                  DESERTAdapter  (TCP, newline-framed, 127.0.0.1:DESERT_PORT)
                        |
            Docker container: server.py -> ns bridge.tcl config.tcl
                        |
 APPLICATION/HOLO -> UDP -> routing -> IP -> HoloProbe -> MLL -> MAC -> PHY (observer)
                        |
        channel + propagation + interference (analytic, WOSS, optical or EM)
```

Per tick `k` (orchestrator and `NetworkSession.step`):

1. Send the HoloOcean poses measured at `t_k` (`POSITION`, timestamp `t_k`).
2. Apply due power events (`POWER`).
3. Run the applications with their own pose and the deliveries already due,
   then inject the generated messages (`SEND`).
4. Request statistics once per simulated second (`STATS`).
5. HoloOcean advances one physics tick; DESERT runs its own scheduler up to
   `t_(k+1)` (`STEP`) and returns every event with its NS timestamp.
6. The client checks that DESERT stopped exactly at `t_(k+1)` and acknowledged
   every position; `rx` events are queued and delivered to applications when
   the logical clock reaches their timestamp.

`bridge.tcl` holds the NS scheduler inside a Tcl `barrier` callback: it reads
commands, then schedules the next barrier with `$ns at` and returns to the
original scheduler, which executes **all** internal events up to that barrier.
`$ns run` is never re-invoked, the queue is never reset and no Python
propagation delay is imposed. Geometry is constant within a tick
(left-sampled); see
[telemetry-and-reproducibility.md](telemetry-and-reproducibility.md#time-quantities).

Coordinates: `DynamicsSensor` with `UseCOM=true` gives metres in the HoloOcean
frame (X forward, Y left, Z up). DESERT uses Cartesian metres with negative Z
below the surface; `CoordinateConverter` applies this identity with an optional
common origin shift. Unreal centimetres and the IMU socket's NED orientation are
not used.

## Engine bridge protocol

Transport: TCP to `127.0.0.1:<DESERT_PORT>` (container port 5555), one
newline-terminated line per message. Engine events are JSON lines starting
with `{"event":`.

### Session opening (`server.py`)

| First line | Behaviour |
|---|---|
| `HEALTH` | Replies `{"event":"health","backend":"desert","release":"4.0.0","engine_fingerprint":…,"desert_base_image":…}` and closes. Handled by `server.py`, not by the bridge |
| Scenario JSON (`Scenario.model_dump_json()`, read up to 131072 bytes) | Acquires the single-session lock (2 s timeout, else `{"event":"error","reason":"DESERT is busy"}`); validates with `stack_builder.validate`; emits `engine_info`; renders `config.tcl` into a new temporary directory; starts `ns /opt/holo/desert/tcl/bridge.tcl config.tcl` |

Afterwards `server.py` forwards each client line (≤ 20000 bytes) to the NS
process's stdin and each `{"event":…}` line from NS to the client; other output
(library banners) goes to the container log. When NS exits it sends
`{"event":"engine_exit","code":…}`. Closing the connection terminates the NS
process. Validation errors are returned as `{"event":"error","reason":…}`.

### Bridge commands (`bridge.tcl`)

At each barrier the bridge prints `{"event":"barrier","time":<t>}` and reads
commands until `STEP` or `STOP`.

| Command | Arguments | Effect / events |
|---|---|---|
| `POSITION` | `node x y z state_time [yaw [pitch roll]]` | `state_time` must equal the barrier time; angles in radians (used by the optical adapter). Updates `Position/BM` (or WOSS geographic position) → `position_applied` |
| `SEND` | `src dst hex` | Hex-encoded envelope (≤ 4096 bytes) injected by `Module/UW/APPLICATION/HOLO sendhex` on the scheduler thread → `app_tx`, then native stack events |
| `POWER` | `node value` | Acoustic dB SPL (0–200), optical W (1e-15–10000) or EM dBm (−100–100) → `power_applied` |
| `INTERFACE` | `node index` | Manual multi-PHY switch; requires an idle controller and empty MAC queue → `interface_selected` |
| `STATS` | – | `stats` and `mac_specific_stats` per node, plus `routing_stats` (SUN), `ranging_estimate` (Ranging-TokenBus), `interface_state` (multi-PHY) |
| `STEP` | `target` | `target > now`; schedules the next barrier and returns to the NS scheduler |
| `STOP` | – | Closes WOSS databases if used and exits |

Node arguments are DESERT addresses `1..N` (scenario file order); numeric
arguments must be finite. Any invalid command writes the reason to the engine
log, emits `{"event":"error","reason":"invalid bridge command; see engine log"}`
and exits with code 2. The client (`DESERTAdapter`) raises `BackendError` on
`error`/`engine_exit`, on a wrong barrier time and on a closed stream.

Python methods: `start(scenario)`, `update_node_position(node, pose, t)`,
`send(message)`, `set_power(node, value)`, `set_interface(node, interface)`,
`request_stats()`, `advance(target)`, `stop()`, `health_info()`.

### Why a project application module

The official `uwApplication` socket interface (DESERT 4.0.0,
`application/uwApplication/`) was analysed before writing the bridge. Its TCP
mode creates one packet per `read` (not per message; `MAX_READ_LEN` default 64,
header limit 4096), serves one client per instance, and takes the destination
from instance properties (`destAddr_`, `destPort_`) rather than per frame; its
UDP output writes to the TCP client descriptor. Positions and the NS scheduler
are not reachable through the socket. Measured with the unmodified image:
`holo-desert official-sample` sent and received 166 packets;
`holo-desert official-sockets` exchanged payloads in both directions over TCP
(counters `PROBE_SENT=1,1`, `PROBE_RX=1,1`), while over UDP the same stack
counters increased but no payload returned to the external clients.

The bridge therefore uses `Module/UW/APPLICATION/HOLO`, a subclass of the
official application: `sendhex` injects a v1 envelope on the scheduler thread
with the official IP/UDP/APPLICATION headers (header priority 0; the sequence
number is kept inside the upstream lookup range and is independent of the
message UUID), and `recv` reports the NS time and bytes before delegating to
the official accounting. `Module/HoloProbe` is a transparent observer below IP
that reports downward packets (forwarding at relays) without changing routes.
Positions are written to the same `Position/BM` objects registered in
`PlugIn/PositionDB` that the channel reads, on the scheduler thread. The
extension links the upstream libraries explicitly through `DT_NEEDED`.

## Applications inside the orchestrator

`SimulationOrchestrator(scenario, application_factory=…)` (also accepted by
`ManagedSimulation`) builds one application per node with
`factory(node, communication, scenario)`. An application implements
`update(now, own_pose, received)` and may return a HoloOcean controller target
`(x, y, z, roll, pitch, yaw)` (a target for the official controller, not an
imposed pose) or `None`. An optional `snapshot(now)` returns local metadata
shown by the dashboard and must not mutate state.

```python
from holo_desert.core.orchestrator import SimulationOrchestrator
from holo_desert.scenarios.config import ScenarioManager

class DepthReporter:
    def __init__(self, comm, peer):
        self.comm, self.peer, self.next_send = comm, peer, 1.0

    def update(self, now, own_pose, received):
        if now >= self.next_send:
            self.comm.send(self.peer, {"depth_m": -own_pose.z}, ttl=8)
            self.next_send = now + 3
        return None

scenario = ScenarioManager().load("e01_chat")
def factory(node, comm, configuration):
    peer = next(n.id for n in configuration.nodes if n.id != node.id)
    return DepthReporter(comm, peer)

run = SimulationOrchestrator(scenario, application_factory=factory)
try:
    run.run()
finally:
    run.close()
```

The communication handle (`DroneCommunication`) offers `send(destination,
bytes | dict, ttl=…, priority=…, message_type=…)`, `send_json(destination,
value)` and `receive()` (returns and clears the node's inbox). Unicast only;
unknown or identical source/destination raise before injection. Transmit and
receive queues are bounded to 1000 messages (`BufferError` on transmit;
`bridge_receive_overflow` event on receive). Duplicates are filtered by message
ID within the validity window; a message arriving after its TTL produces
`late_receive` and is not delivered.

New vehicles: add a profile to `holoocean_adapter/vehicles.py` implementing
`configuration(node)`, `pose(sensors)` and `action(target)`, register it in
`VEHICLE_PROFILES` and extend the accepted `Node.vehicle` values. The
orchestrator does not change. Units, orientation, frame, sensors and controller
must be verified with the real vehicle; only `HoveringAUV` is currently
accepted and validated.

## Running tests

| Suite | Location | Marker / command | Requires |
|---|---|---|---|
| Unit | `tests/unit` | `holo-desert test` (`-m "not desert and not holoocean"`) | nothing |
| Native DESERT | `tests/integration` | `holo-desert test --integration` (`-m "desert and not holoocean"`) | Docker; builds the extension against the real DESERT headers |
| End-to-end | `tests/end_to_end` | `holo-desert test --end-to-end` (`-m holoocean`) | Docker, HoloOcean 2.3, Ocean, GPU |
| Everything | | `python -m pytest -q -m "desert or not desert"` | all of the above |
| Browser | `tests/frontend` | `npm ci` then `npm test -- --config playwright.config.cjs` | Node, Playwright 1.64.1; Edge on Windows, Chromium on Linux |

Markers are declared in `pyproject.toml` (`desert`: real DESERT Docker service;
`holoocean`: Ocean and a GPU). The session fixture `engine` in
`tests/conftest.py` skips real-simulator tests unless `-m desert` or
`-m holoocean` is selected. If no healthy engine answers, it starts the default
Compose service and stops it afterwards.

**Isolated engines.** Set `DESERT_PORT` to run tests against a separate,
already healthy engine (for example a second container of the engine image
publishing `127.0.0.1:5559:5555`). With `DESERT_PORT` set and no healthy
service, the fixture fails instead of touching the default Compose project:

```powershell
$env:DESERT_PORT='5559'
.venv\Scripts\python.exe -m pytest tests/integration/test_native_media.py -m desert -q
```

The engine-death test kills `ns` only in the container publishing the test port,
or in the container named by `DESERT_TEST_CONTAINER`.

**Frontend tests** start `python -m holo_desert dashboard` on port
`HOLO_UI_PORT` (default 8011) with `HOLO_DESERT_SCENARIOS_DIR` set to
`.local/ui-test-library`; never point them at a real personal library. Failure
artefacts go to `.local/ui-test-results/`. Presentation fixtures intercept
requests in the browser only and show an explicit banner.

**CI** (`.github/workflows/tests.yml`): unit tests on Ubuntu 24.04 with Python
3.10 and 3.12; a package job that builds the wheel, installs it in a clean venv
and runs `examples/external_app/check_install.py` with `python -I`; and the
Chromium browser suite (see [troubleshooting.md](troubleshooting.md#installation-and-tests)
for the apt-source workaround). Engine and HoloOcean tests are not run in CI.

**Validation scripts** (require a running engine): `scripts/validate_channel.py`
(DESERT only), `scripts/validate_examples.py` (HoloOcean + DESERT),
`scripts/validate_dashboard.py` (HTTP path of an idle dashboard); see
[telemetry-and-reproducibility.md](telemetry-and-reproducibility.md#reproducing-the-reference-examples-e01e06).

**Packaging.** Before a release check `pip wheel . --no-deps` and the wheel
contents (catalogue, inventory, Tcl adapters, C++ headers, frontend modules).
Do not add Ocean binaries, DESERT copies, generated outputs or virtual
environments to the repository.

## Adding a new DESERT adapter

The existing adapters (for example CS-Burst, TokenBus, SUN, WOSS, optical/EM,
multi-PHY, native CBR/VBR) are wired through the same chain. Adding a name to a
selector is not an integration: each step below is required.

1. **Audit the module in the pinned image.** Confirm the source, compiled
   library, `TclClass` names, bindings and their defaults in the container
   (`desert-inventory.json` records the audit). Read the official sample and
   the C++ to determine what must be set before the constructor, what per
   instance, which timers must be started and which libraries must be loaded
   explicitly (the installed Tcl loads plugins `RTLD_LOCAL`; missing
   `DT_NEEDED` siblings must be loaded by the adapter).
2. **Catalogue entry.** Add the module to
   `resources/docker/communication-catalog.json`: `id`, `layer`, `tcl_class`,
   `libraries`, `description`, `initialization`, `compatibility` (MAC, routing,
   PHY, media), `telemetry`, `validation`, `experimental`, `operational` and a
   `parameters` list (`path`, `type`, `default`, `unit`, `min`, `max`, `help`).
   `stack_builder.defaults()` fills missing values from these defaults and
   `validate()` range-checks every registered parameter; only registered
   controls can reach generated Tcl.
3. **Pydantic model.** Add the typed parameters with the same defaults, units
   and bounds (`scenarios/network.py`, `protocols.py`, `media.py` or
   `environment.py`; `extra='forbid'`, `allow_inf_nan=False`) and the
   cross-field rules in `Network.supported_stack`.
4. **Stack builder whitelist and render.** In `stack_builder.py` register the
   class and libraries (`MACS`, `ROUTING`, `PHYS`, or a dedicated
   `*_config.py` validator), repeat every compatibility rule (the builder also
   validates raw JSON received over TCP, without pydantic), add the allowed
   parameter keys and render them as numeric Tcl variables with `number()`.
   Include feasibility checks that depend on frame size where relevant (as for
   TDMA slots and TokenBus holding times).
5. **Tcl adapter.** Add `resources/desert/tcl/modules/mac_<adapter>.tcl` (or
   `routing_*`, `environment_*`) implementing the hooks used by `bridge.tcl`:
   `prepare_mac` / `create_mac i` / `start_macs` (MAC), `prepare_routing` /
   `initialize_routing i` / `configure_routes` and optionally `create_routing i`
   (routing). Set `mac_queue_command` and `mac_stat_commands` for the native
   queue and counters; add an `observe_*` procedure for extra `STATS` output.
6. **Bridge events and telemetry.** If the module creates new packet types or
   headers, extend the observer classes in `extensions/` so that PHY events
   identify data versus control frames and carry the application payload or
   native packet ID; build-time source assertions should reject a different
   upstream implementation. Make the collector understand any new event
   fields; never synthesise values the native module does not expose.
7. **Engine fingerprint.** Any file copied into the image, the `Dockerfile`
   and the base image reference are covered by `engine_fingerprint()`; a new
   file in `resources/docker/` must be added to `ENGINE_FILES` and to the
   `Dockerfile` `COPY` line (a unit test compares the two). Rebuild with
   `holo-desert engine up`.
8. **Tests.** Unit tests for schema and builder acceptance/rejection
   (`tests/unit/test_stack_builder.py`, `test_additional_protocols.py` as
   models); native tests under `tests/integration` with `-m desert` that send
   real packets in both directions, restart the process, exercise the queue and
   parameters, and check rejected combinations; an end-to-end HoloOcean test
   before declaring the module operational.
9. **Documentation and status.** Update the catalogue status (`validation`,
   `experimental`, `operational`, `reason`),
   [stack-configuration.md](stack-configuration.md) and
   [capabilities.md](capabilities.md). Use the status vocabulary of
   [stack-configuration.md](stack-configuration.md#status-vocabulary); do not
   call a module operational before its end-to-end verification.
